# ADR-0010: Per-node NATS credentials with decentralized JWT authentication

- **Status**: Proposed
- **Date**: 2026-11-28

## Context

Every NATS client on the hub is trusted alike (ADR-0007). Any edge node could publish
another node's status or heartbeats, or read every node's desired state. ADR-0002 deferred
per-node credentials to Phase 3. The constraints:

- **Nodes join and leave.** A new satellite must not need a hub reconfiguration or
  restart, and the hub may be unreachable when a node is provisioned.
- **One leaf connection per node.** Its credentials and permissions cover everything on
  that node (agent and payload), as ADR-0002 already notes.
- **JetStream through the leaf.** The agent watches its KV key and publishes status in
  domain `hub`. These need JetStream API permissions, which are easy to get wrong in both
  directions.
- **No secret in Git, Terraform state or VM metadata**, and Claude never reads or prints
  one.

## Decision

- **Decentralized JWT authentication**: an *operator*, an `ORBIT` account, and one *user*
  per node, plus one for the operator process.
  - **The hub knows only public JWTs**: the operator's and the accounts' (memory
    resolver, preloaded).
  - **User JWTs are signed offline** with the account key. Adding a node changes nothing
    on the hub; removing one adds its key to the account's revocation list.
- **Per-node permissions, deny by default**, written once in Go:
  - **publish** only on `orbit.edge.<node>.>`, plus the JetStream API calls the agent needs
    for its own KV key;
  - **subscribe** only on its own inbox prefix `_INBOX_<node>.>`. The agent uses that
    prefix, so a node cannot read another node's replies.

  The same code (`agent/internal/natsauth`) is used by the agent's integration tests, which
  run its real transport through a leaf node, and by the tool that issues credentials,
  `orbit-creds` (`agent/cmd/orbit-creds`). The tests prove what works and what is denied.
- **Where secrets live**:
  - **Offline**: the operator and account seeds stay on the administrator's machine, in
    `0600` files outside the repository.
  - **In each cluster, created at bootstrap**:
    - the hub's public JWT configuration and the operator's credentials, on the hub;
    - each node's credentials, on that node.

    Like the per-cluster ConfigMaps (`gitops/README.md`), these are Kubernetes Secrets.
  - **Delivery to the cloud VMs** goes through Secret Manager (#90): each VM reads only its
    own secret.
- **docker compose stays unauthenticated**: it is the local development loop.

## Alternatives considered

- **Static NKeys in the server config** (`authorization` / `leafnodes.authorization`). Every
  new node changes `nats.conf` and reloads the hub, so the hub's config becomes per-fleet
  state. Revocation is an edit too.
- **Username and password per node.** Same reconfiguration problem, and a shared secret on
  both sides instead of a key pair.
- **mTLS with per-node certificates.** It authenticates nodes, but subject permissions
  still need an authorization layer mapping certificates to users. It also adds a CA to
  run. It can be layered on later for transport encryption.
- **Issuing credentials with `nsc` scripts.** That is the standard tool, but the
  permissions would live in shell arguments, apart from the tests that prove them.
  `orbit-creds` keeps one definition, and the resulting `.creds` files stay compatible
  with `nsc` and `nats` tooling.

## Consequences

- ➕ **Least privilege for each node**: a compromised satellite can only speak for itself.
- ➕ **No hub change to add a node**: provisioning works while the hub is unreachable.
- ➕ **Tested permissions**: the JetStream API surface the agent needs is written down and
  covered by tests.
- ➖ **Key management.** Losing the account seed means re-issuing every node's credentials.
  - Mitigation: back up the seeds offline; the runbook (#91) covers it.
- ➖ **Expiry and rotation.** User JWTs can expire; Phase 3 issues them without expiry.
  - Mitigation: revocation per node; expiry and rotation are a later step.
- ➖ **Partial coverage.** The local docker compose fleet does not exercise authentication.
  - Mitigation: the k3d fleet does, with throwaway credentials generated by
    `make fleet-up`.
- ➖ **Two inbox prefixes in use.** The agent's custom prefix must match its permissions.
  - Mitigation: `orbit-creds` lives in the agent module, so they share one constant, and the
    integration tests run the agent's real transport.
